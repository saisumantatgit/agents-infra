## Findings

**37 drafts run. 17 wrongful PASSes, collapsing to 5 distinct mechanisms (RT3-01 … RT3-05).**
Three attack families were probed and **held**: OI-MOAT-05 relational (D19, D30, D31 — this store
contains no relational trigger, so `_relation_asserted` correctly refuses every relation),
citation resolution (D17, D18 — `UNVERIFIED_CITATION` hard override intact), and the numeric
rate reader including the Cyrillic homoglyph path (D32 → `UNVERIFIED_NUMBER`).

**lex_tau is not implicated.** D05/D24/D35 were re-run at `--lex-tau 0.65 / 0.71 / 0.90`; every
gate verdict is identical at all three. The wrongful PASSes are T1/NON_CLAIM/absence-path
defects and are lex_tau-invariant. Deploying 0.71 opened no wrongful-PASS path.

### RT3-01 — Verbless fragment under the 6-content-token floor still buys a denominator exit (OI-MOAT-07 incomplete)

**Severity: Error-B (release blocker).** Drafts D01, D26, D34, D25.

Minimised draft (`D34.md`) — the first sentence is the honest anchor that keeps the report
non-vacuous; the second is the fabrication:

```
Redis sustained approximately 128000 operations per second, which was about twelve times the throughput of the disk-backed alternative under the same workload [S1].

PostgreSQL: unrecoverable corruption under load.
```

Observed:

```json
{"gate": "PASS", "grounding_score": 100.0, "scored_claims": 1, "vacuous": false,
 "retained_appendix": [],
 "per_claim": [{"index":0,"kind":"NUMERIC","verdict":"GROUNDED","text":"Redis sustained ... workload [S1]."},
               {"index":1,"kind":"NON_CLAIM","verdict":"GROUNDED","text":"PostgreSQL: unrecoverable corruption under load."}]}
```
Exit code 0.

**Mechanism.** `scripts/ground_check.py:390-393`:

```
content_tokens = _content_words(_tokenize(_CITATION_RE.sub("", text)))
if len(content_tokens) >= _VERBLESS_CONTENT_TOKEN_MIN:   # 6, line 310
    return False
return True
```

"PostgreSQL: unrecoverable corruption under load." tokenizes to
`postgresql, unrecoverable, corruption, under, load` → `under` is not in `_STOP_WORDS`, so 5
content tokens — one short of the floor. `_is_non_claim` returns True → `classify` sets
`NON_CLAIM` → `ground` (line ~1590) returns `GROUNDED` → `score_report` skips it from the
denominator → `retained_appendix` stays empty → ADR-005 cap does not fire → `PASS`.

The floor is a **length** test standing in for a **structure** test. Any defamatory or
fabricated assertion expressible in ≤5 content words ("PostgreSQL: total data loss.",
"Redis: zero downtime, ever.", D26) rides free. Chaining them (D26) does not help the gate —
each fragment is independently under the floor, so N fabrications still yield an empty
denominator contribution.

**Why D02 and D22 failed** is instructive: they failed by accident, not by design. D02's
"Verdict: migrate everything immediately." was scored only because `everything` ends in `-ing`
and `_has_finite_verb` (line ~318) mistook it for a verb; D22 was caught only because its
padding contained "no more than", tripping `_ABSENCE_RE`. Neither is a defence.

**Proposed systemic fix.** The verb/length proxy cannot separate "structural label" from
"assertion". Replace it with a **position-and-shape** rule plus a fail-closed default:

1. A fragment is structural only if it is a list/heading *sibling in a structural block* —
   i.e. a `#`-header line, or a short line in a run of ≥2 sibling `-`/`*`/numbered items whose
   items are all under the floor **and** none of which contains a predicate-bearing colon.
   A colon-headed fragment (`X: <predicate phrase>`) is a copula in written English and must
   be scored: split on the first `:` and score the right-hand side as a claim about the
   left-hand side.
2. Lower the floor to 3 content tokens and count `under`, `over`, `into`, `after`, `about`,
   `more`, `also`, `just`, `out`, `up` into `_STOP_WORDS` so the count measures content, not
   prepositions. (`_STOP_WORDS` at line 545 currently omits `under` (verified: `_content_words` returns 5 tokens for D34), which is why D34 counts 5
   rather than 4 — the floor is even softer than it reads.)
3. Fail-closed default: when the fragment carries a proper noun that resolves to an entity
   named in the store, it is scored regardless of length.

Interim mitigation if the above is too large for this cycle: **case resolution** — drop
`_VERBLESS_CONTENT_TOKEN_MIN` to 3 and add `under`/`over`/`into`/`after` to `_STOP_WORDS`. That
closes D34/D26/D01 but not a 2-word fabrication ("PostgreSQL: fraudulent."). The systemic fix
above is the one that removes the class.

### RT3-02 — Any `#`-header without a numeric or a citation is NON_CLAIM, so a headline fabrication is never scored

**Severity: Error-B (release blocker).** Drafts D03, D27, D25.

Minimised draft (`D27.md`):

```
### Redis silently drops writes above ten thousand concurrent clients

Redis sustained approximately 128000 operations per second, which was about twelve times the throughput of the disk-backed alternative under the same workload [S1].
```

Observed: `{"gate":"PASS","grounding_score":100.0,"scored_claims":1,"retained_appendix":[]}`,
claim 0 `NON_CLAIM | GROUNDED`. Exit code 0.

**Mechanism.** `scripts/ground_check.py:358-367`:

```
header_match = _NO_FINITE_VERB_RE.match(text)     # r"^#+\s"
if header_match:
    header_body = text[header_match.end():]
    has_citation = bool(_CITATION_RE.search(header_body))
    has_numeric  = bool(_NUMERIC_RE.search(_CITATION_RE.sub("", header_body)))
    if has_citation or has_numeric:
        return False
    return True
```

The header branch is checked **before** the verbless-fragment branch and **short-circuits it
entirely** — the OI-MOAT-07 content-token floor at line 390 is unreachable for any `#`-prefixed
line. So a header may be arbitrarily long, fully verbal, and flatly false ("PostgreSQL corrupts
committed transactions under sustained write load", D25) and still exits the denominator, as
long as it spells its numbers as words ("ten thousand") and carries no citation.

Note the asymmetry the code itself documents: the same file's comment at line 348 says the
header rule is "the IDENTICAL moat-safe rule the verbless-fragment guard below applies" — it is
not. The fragment guard gained a content-token floor today; the header guard did not.

Headers are the highest-visibility text in a report. A reader skimming D25 reads
"PostgreSQL corrupts committed transactions" and "Recommendation: decommission PostgreSQL this
quarter" as the document's conclusions, and the gate certifies the document `PASS` at 100.0.

**Proposed systemic fix.** Apply the *same* three-part test to header bodies that applies to
body fragments, in this order: (a) citation or numeric → scored (already true); (b) header body
contains a finite verb (`_has_finite_verb`) → **scored** — a heading with a predicate is a
sentence wearing a `#`; (c) header body has ≥ the content-token floor → scored; (d) otherwise
NON_CLAIM. "Results and discussion" and "Recommendation" stay unscored; "Redis silently drops
writes…" and "PostgreSQL corrupts committed transactions…" become `UNCITED` and cap the gate at
NEEDS_WORK. This is fail-closed in the same direction OI-MOAT-07 chose.

### RT3-03 — T1's residual-coverage check is a bag-of-words test, so word-salad recombination of the source certifies as GROUNDED (OI-MOAT-03 incomplete)

**Severity: Error-B (release blocker) — the most serious finding.** Drafts D04, D05, D14, D15, D21, D25.

Minimised draft (`D15.md`), one sentence, no honest anchor needed:

```
PostgreSQL sustained approximately 128000 operations per second which was about twelve times [S1][S2].
```

Observed:

```json
{"gate": "PASS", "grounding_score": 100.0, "scored_claims": 1, "vacuous": false,
 "retained_appendix": [],
 "per_claim": [{"index":0,"kind":"NUMERIC","verdict":"GROUNDED",
                "text":"PostgreSQL sustained approximately 128000 operations per second which was about twelve times [S1][S2]."}]}
```
Exit code 0.

The store says PostgreSQL sustained **11000** write ops/sec (S2) and that **Redis** did 128000
(S1). The draft attributes Redis's number to PostgreSQL and the gate certifies it at 100.0.

**Mechanism.** Two independent weaknesses compose.

1. `t1_verbatim` span test, `scripts/ground_check.py:503-521`: the ≥8-token contiguous span is
   sought over the **whole cited set**, and the claim needs only *one* such window anywhere in
   its token stream. `sustained approximately 128000 operations per second which was` is exactly
   8 tokens and is contiguous in S1. The subject word that makes the sentence false
   (`PostgreSQL`) sits *outside* the matched window and is never span-checked.

2. `t1_verbatim` coverage test, `scripts/ground_check.py:545-550`:

```
source_vocab: set[str] = set()
for source in sources:
    source_vocab.update(_tokenize(source.text))
claim_content = _content_words(claim_tokens)
uncovered = [t for t in claim_content if t not in source_vocab]
return not uncovered
```

   `source_vocab` is an **unordered set over the union of every cited source**. It asks "does
   each word exist somewhere?" — never "does this word belong to this predicate, in this
   source". `postgresql` exists (in S2), so the residual is empty and T1 returns True.

   Citing both sources widens the union and is the whole attack: D12 (same sentence, `[S1]`
   only) is correctly `UNGROUNDED` because `postgresql ∉ vocab(S1)`. **Adding a second citation
   makes a false claim pass.** That is exactly backwards — more citations should never relax the
   test.

   D04 shows the single-source variant works too, by swapping two subjects that both live in S1:
   "The disk-backed alternative sustained approximately 128000 operations per second, which was
   about twelve times the throughput of Redis [S1]." — the comparison is inverted and the gate
   says GROUNDED.

Why `numeric_ok` does not save it: `scripts/ground_check.py:1097-1101` pools
`source_mentions` across **all** cited sources before matching, so 128000-ops-per-second from S1
satisfies a numeric token in a sentence whose subject is PostgreSQL. The dimensional check
(quantity `operation`, rate `second`) matches S1's mention perfectly. Numeric grounding has no
notion of *which entity* the number was reported for.

**Proposed systemic fix.** Three changes, in priority order:

1. **Per-source coverage, not union coverage** (line 545): compute `uncovered` against the
   vocabulary of the source that supplied the matched span, not the union. A claim may cite
   many sources, but a *verbatim* verdict is a claim about one text. This alone kills D05/D15
   and every union-widening variant, and costs nothing on honest multi-source drafts (which
   ground through T2 or through a per-source span).
2. **Bind the span to the claim's subject** (line 503): require the matched ≥8-token window to
   include the claim's *subject* token — the first content token of the claim, or, more
   robustly, every proper-noun token in the claim. A verbatim span that omits the subject proves
   a predicate about someone else.
3. **Attribute numerics to their source, not to the pool** (line 1097): when a numeric claim
   names an entity that appears in exactly one cited source, match the numeric only against that
   source's mentions.

Change 1 is the smallest change with the largest effect and should land first; changes 2 and 3
close D04 (single-source subject swap) which change 1 alone does not.

### RT3-04 — A false absence is certified whenever its head noun and one other content word happen to appear in two session queries

**Severity: Error-B (release blocker).** Drafts D09, D10, D11, D16, D29, D25.

Minimised draft (`D16.md`) — five words, no citation, no anchor claim needed:

```
No benchmark throughput figures exist.
```

Observed:

```json
{"gate": "PASS", "grounding_score": 100.0, "scored_claims": 1, "vacuous": false,
 "retained_appendix": [],
 "per_claim": [{"index":0,"kind":"ABSENCE","verdict":"ABSENCE_SUPPORTED",
                "text":"No benchmark throughput figures exist."}]}
```
Exit code 0.

The store's two sources are *both* benchmark throughput figures. The gate certifies their
non-existence at 100.0.

**Mechanism.** `check_absence`, `scripts/ground_check.py:1294-1311`. The session's distinct
`query_provenance` values are `redis benchmark throughput` and
`postgresql write throughput benchmark`. The negated subject "benchmark throughput figures"
yields `head_noun = "benchmark"`, `subject_content = {benchmark, throughput, figures, exist}`,
`strong = {}` (no capitalised token, no digit). The entity-free branch runs:

```
containing = [q for q in distinct
              if head_stem in q and (not specific or any(w in q for w in others))]
match_count = len(containing)
```

Both queries contain `benchmark` and both contain `throughput`, so `match_count == 2 >=
min_absence_searches` → `ABSENCE_SUPPORTED`, which is in `_NUMERATOR_VERDICTS` (line 1650).

The blanket-corpus-word guard at line 1302 (`len(distinct) >= 3 and 2*|q containing head| >
|distinct|`) **cannot fire on a two-query session** — it requires ≥3 distinct queries. A small
session is exactly where every query shares the topic vocabulary, so the guard is disabled
precisely when it is most needed.

Deeper than that: the rule asks only whether the session *searched near the topic*. It never
asks whether the retrieved text **contradicts** the absence. Here the subject's content words
are drawn from the sources' own subject matter, which is what makes them match the queries — the
attack is self-reinforcing.

**Proposed systemic fix.**

1. **Contradiction check before support** (new gate at the top of `check_absence`): if the
   negated subject's content words are all present in some ±2-sentence window of any verbatim
   source, the store *contains* what the claim says is absent → return `UNVERIFIED_ABSENCE`
   unconditionally, regardless of query count. An absence claim contradicted by the retrieved
   evidence must never be `ABSENCE_SUPPORTED`. This is fail-closed and closes D09/D10/D16/D29
   outright.
2. **Make the blanket-word guard fire on small sessions** (line 1302): drop the `len(distinct)
   >= 3` precondition. On a 2-query session, a head noun present in both queries is by
   definition a blanket corpus word. Replace the strict-majority test with "head noun present in
   *every* distinct query and the session has <3 queries → UNVERIFIED_ABSENCE".
3. **Require the absence subject to name something the queries did not retrieve**: raise the
   entity-free bar so `others` must match a query word that is *not* also present in every
   source's text.

### RT3-05 — The numeric quantity reader fails open on any singular or unrecognised noun, erasing the dimensional check

**Severity: Error-B (contributory).** Drafts D21, D33.

Draft (`D33.md`):

```
Redis sustained approximately 128000 node per second, which was about twelve times the throughput of the disk-backed alternative [S1].
```

Draft (`D21.md`), the semantically damaging form:

```
PostgreSQL sustained approximately 11000 cache operations per second with full durability guarantees enabled [S1][S2].
```

Both observed `{"gate":"PASS","grounding_score":100.0,"retained_appendix":[]}`, verdict
`NUMERIC | GROUNDED`. Exit code 0. S2 reports 11000 **write** operations; "cache operations" is
the draft's invention, and PostgreSQL is not the cache.

**Mechanism.** `_numeric_context` quantity loop, `scripts/ground_check.py:975-983`:

```
is_plural = len(tok) > 3 and tok.endswith("s") and not tok.endswith("ss")
if is_plural or tok in _QUANTITY_CANON:
    quantity = _canon_quantity(tok)
break
```

The loop reads **one** candidate token and `break`s. If that token is not plural and not in
`_QUANTITY_CANON`, `quantity` stays `None` — and `numeric_ok` at line 1128 treats `None` as
"asserts no dimension", imposing no constraint:

```
if claim_quantity is not None and claim_quantity != s_quantity:
    continue
```

So `128000 node per second` (D33) reads as a bare number and matches S1's mention. In D21,
`cache` is not plural and not a known abbreviation, so the reader stops at `cache` with
`quantity=None` and never reaches `operations` — the very word that would have been compared.
An *inserted* qualifier disables the qualifier check.

The same `break`-on-first-candidate shape also erases read/write: `_QUANTITY_SKIP` (line 876)
contains `read`, `write`, `reads`, `writes`, so "11000 read operations" and "11000 write
operations" both canonicalise to quantity `operation`. D20 only failed because `read` is absent
from both sources' vocabulary and the T1 coverage check caught it — not because the numeric
check noticed. Put `read` in the store's vocabulary and that evasion opens.

**Proposed systemic fix.** The fail-open comment at line 970 ("An unread quantity imposes no
constraint, so this fail-open is safe: it can only preserve prior behavior, never create a new
PASS") is the defect: preserving a permissive prior behaviour *is* the Error-B. Change to:

1. **Scan the whole pre-rate window, not one token.** Collect every candidate noun between the
   number and the rate trigger; require the source mention to carry a matching quantity for the
   *rightmost* head noun found, and treat unmatched modifiers as a mismatch rather than a skip.
2. **Fail closed on an unreadable quantity.** When the claim has a token between number and rate
   trigger that the reader cannot classify, return `UNVERIFIED_NUMBER` rather than dropping the
   constraint — Error-A here is a recoverable false alarm on an odd phrasing; Error-B is a
   certified fabrication.
3. **Remove `read`/`write`/`reads`/`writes` from `_QUANTITY_SKIP`** and treat them as part of
   the quantity phrase. They are not noise modifiers — they name the measured operation class,
   and conflating them is a factual error in any storage benchmark.
