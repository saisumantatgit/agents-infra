## R12-01 — ERROR-B, CRITICAL. J-44's stem collides, and J-39's longer phrase pays for it

The conclusion-first file argues J-44 is safe because the longer needle J-39
installed means "every modifier must still be present and only the number is
forgiven". That argument fails when the head noun is matched by a COLLISION and
the modifier is a word the unrelated source happens to contain. `_stem` strips
one trailing `s` with no part-of-speech test, so it maps the noun **`news`** to
the adjective **`new`** — one of the highest-frequency words in English prose.

Draft (a fabricated causal claim; neither source says a recall caused news
coverage):

```
The recall causes negative news [S1][S2].
```

Store:

```python
[rec("S1","Brokers said the new coverage limits leads to negative margins for "
          "small carriers. The policy recall provision was rewritten last year "
          "and nothing else changed."),
 rec("S2","A product recall notice was issued for the affected batch in March.")]
```

Observed:

```
HEAD   F8b stem collision, anchor IS the collision          gate=PASS   GROUNDED
PRE    F8b stem collision, anchor IS the collision          gate=FAIL   UNVERIFIED_RELATION
```

Mechanism, isolated:

```
MODE HEAD
 extract_arguments: ('recall', 'negative news')
 _endpoint_in_window(window,'negative news') = True
 _contains_word(window.lower(),'news') = False      <-- literal match FAILS
 _stem('news') = new                                <-- stem match SUCCEEDS
MODE PRE
 extract_arguments: ('recall', 'news')              <-- single token, literal, refused
```

This is a proven regression: PRE refused, HEAD certifies. It refutes claim 1 of
the conclusion-first file.

The collision class is not a single word. Same mechanism, verified at unit
level: `_endpoint_in_window("A specie of coin was found.", "species") → True`;
`_endpoint_in_window("A strong work ethic was praised.", "ethics") → True`;
`_endpoint_in_window("Len Smith wrote the report.", "lens") → True`;
`_endpoint_in_window("the clause causes damage to the roof", "damages") → True`
(in law, *damages* and *damage* are different things).

Proposed fix, as prose: the stem may only be consulted when BOTH forms are
present as a true number pair, which the moat cannot know — so the honest
version is an allow-list of stem pairs the corpus actually needs, or a rule that
the stem match is permitted only for a token that is NOT the phrase's head (the
collisions all occur on the head). The cheapest correct move is to require that
at least one token of a multi-token endpoint match LITERALLY, which keeps the
J-44 migraine case (modifier `severe` matches literally) and kills R12-01
(`negative` matches literally, `news` does not — so the current rule passes;
therefore the stricter variant must be: the HEAD token must match literally).

## R12-11 — ERROR-A, MEDIUM. Function words the new lexicon does not list

Prediction 1 said a missing member of `_ENDPOINT_PHRASE_STOPS` is an Error-A.
Reproduced:

```python
g.extract_arguments("The pipeline causes data loss across regions")
```

of the missing ones. Reusing two sets instead of one does not make the union

## R12-13 — TEST-DEFECT, MEDIUM. The recorded residue misclassifies R12-05

`test_a_vague_quantifier_is_still_not_checked` (strict xfail) states the J-43
residue as: *"'almost all', 'the vast majority', 'nearly every' are an OPEN
class … enumerating them IS the trap the number-word set avoids by being a
lexicon."* That is sound for vague quantifiers. It is NOT what R12-05 is:
`thousands`/`hundreds`/`millions` are inflected members of the closed cardinal
lexicon the ADR argues for. Because the residue is recorded under the

closed-lexicon omission, and a reader of the test file would conclude the
magnitude class is as closed as it can be. A second strict xfail for the
pluralised scale words, with R12-05's repro, would make it a tripwire.

## R12-14 — TEST-DEFECT, LOW. A near-vacuous AST assertion

```python
assert "_contains_word" in names, "triggers must be matched literally"
assert "_stem" not in names, "_relation_asserted must not stem anything"
```

The second assertion inspects only `_relation_asserted`'s own body. `_stem` is
never a plausible direct call there — the stemming the test is named for happens
inside `_endpoint_in_window`, one frame down, and the test cannot see it. It
would therefore pass unchanged if `_endpoint_in_window` were made to stem
triggers too (the only thing holding that line is the first assertion, which
catches removal of `_contains_word` but not an added `or`-branch beside it). The
test's name — "stemming is confined to the endpoint predicate" — asserts a
property about the whole branch that the assertion does not reach.

The sibling AST test in the J-39 file
(`test_window_supports_and_relation_asserted_use_the_same_predicate`) is sound:
it checks a positive structural fact that would genuinely break if the seam
re-opened.

I checked the other guards in the two files against PRE and they are proven
red, not tautologies — `test_the_modifiers_are_still_required_with_stemming_on`
PASSes at HEAD and would FAIL at PRE (PRE endpoints `('pipeline','loss')` are
both in its fixture, with a trigger), and
`test_a_relation_trigger_is_NOT_stemmed` genuinely discriminates (if triggers
were stemmed, "one cause under study" would satisfy the predicate).

## UNVERIFIED SUSPICIONS

Stated as suspicions because I did not turn them into a verdict:

1. **Clause-break punctuation read off the RAW token** (prediction 2). I
   confirmed the mechanism — `raw.rstrip("\"')]}").endswith((",", ";", ":", "—", "–"))`
   fires on the token, not on syntax — but every candidate I tried
   (parentheticals, quoted phrases, `U.S.`, `9:30`, namespaced identifiers)
   either did not end in a break character or broke where a clause really did
   end. I could not build a case where a non-clause punctuation mark truncates
   an endpoint. NOT_LOCATED_UNDER: parentheticals, quotation, abbreviation,
   time/ratio colons, `namespace:value` identifiers.
2. **Em-dash appositives.** `A — a legacy system — causes B` should truncate
   side_A at the dash. I did not construct a store for it.
3. **`_is_quantity_token` on `/`-joined tokens.** `token.replace("/", "-")`
   means `2/3` and `and/or`-style tokens are judged part-by-part; I suspect a
   token like `50/50` or `9/11` is treated as a quantity and dropped from an
   endpoint. `9/11` as an endpoint identifier would then vanish. Not reproduced
   end-to-end (the numeric guard probably backstops it, as in R12-18 below).
4. **Multi-sentence window spanning two sources' boundaries.** Not applicable
   as written (windows are per-source), but `_split_sentences` on a source with
   no terminal punctuation collapses to one window covering the whole document,
   which would make R12-04 easier. Not measured.

## WHAT I COULD NOT BREAK

Specific, and this is where the moat actually holds:

1. **The numeric branch is a genuinely strong backstop, and it is what stops the
   quantity-token skip from becoming Error-B.** Prediction 3 (identifiers
   dropped from endpoints) is CORRECT as a mechanism — `extract_arguments("The
   S3 bucket policy causes silent data loss")` → `('bucket policy', 'silent data
   loss')`, and `"The Type 1 error causes silent data loss"` → `('type error',
   …)`. But every attempt to exploit it failed, because the dropped digit is
   still a `claim.numeric_tokens` entry and `numeric_ok` demands a value+unit+
   dimensional-context match in a CITED source:
   ```
   F15 S3 identifier dropped                             gate=FAIL  UNVERIFIED_NUMBER   (numeric_tokens: ('3',))
   F6  type 1 grounded by type 2                         gate=FAIL  UNVERIFIED_NUMBER
   F6b type 1 vs type 2, digit elsewhere ("1 in 10")     gate=FAIL  UNVERIFIED_NUMBER
   F6c type 1 vs type 2, bare "1" present ("Phase 1")    gate=FAIL  UNVERIFIED_NUMBER
   ```
   The dimensional-quantity rule (OI-MOAT-01) is what kills F6b/F6c: the
   source's `1` carries a different measured quantity. That is a real, earned
   defence and it is the reason D-65's digit-skip is not a hole today. It is
   also a COUPLING worth naming: the endpoint rule is safe only because the
   numeric rule is strict, and nothing in the code records that dependency.
2. **The `"and"` evasion of J-43 is blocked — by the decomposer, not by J-43.**
   `_spelled_quantity_phrases("causes two hundred and fifty million in losses")`
   → `('two hundred', 'fifty million')`, which a source carrying the two runs
   separately would satisfy. But `decompose` splits the sentence at the
   conjunction, producing a RELATIONAL claim and a separate FACTUAL claim, and
   the FACTUAL half reads `UNGROUNDED`:
   ```
   F4 'and' splits spelled run   gate=FAIL   UNVERIFIED_RELATION  UNGROUNDED
   ```
   The docstring's reasoning ("both runs still occur contiguously inside an
   honest source") is not what saves it. The defence is in another component,
   and a decomposer change would silently open it.
3. **The canonical J-39 attack is genuinely fixed.** The exact fixture from
   `test_moat_j39_endpoint_phrases.py` flips PRE→HEAD:
   ```
   HEAD   J39 canonical (must refuse)   gate=FAIL   UNVERIFIED_RELATION
   PRE    J39 canonical (must refuse)   gate=PASS   GROUNDED
   ```
   The phrase extension does what it claims against a source that merely shares
   one common noun per side.
4. **J-43 does close the digit-free figure.** `F5b` above: PRE PASS → HEAD
   `UNVERIFIED_NUMBER`, and the positive control
   (`test_a_spelled_figure_the_CITED_SOURCE_CARRIES_still_certifies`) means it is
   a check, not a ban. The split-across-sources refusal also holds.
5. **Triggers are not stemmed.** I could not find any path by which the trigger
   lexicon reaches `_stem`: `_relation_asserted` calls `_contains_word` on the
   raw window for triggers, and `_endpoint_in_window` is only ever called with
   `a`/`b`. Searched three ways — by name (`grep -n "_stem"`), by call graph
   (reading every caller of `_endpoint_in_window` and `_contains_word`), and by
   behaviour (the "one cause under study" fixture, which stays
   `UNVERIFIED_RELATION`).
6. **Empty endpoints fail closed.** `_endpoint_in_window(w, "")` is False;
   `extract_arguments` returns None when a side reduces to nothing (verified for
   an all-quantity side: `"H5N1 causes …"` → side_A empty → `None`), and
   `spelled_quantity_ok` returns False with phrases and no sources. Claim 3 of
   the conclusion-first file is correct for the three branches it names.
7. **Store integrity.** Nothing I did could make an unresolvable citation, a
   `haiku_summary` source, or a sub-2-source relational claim certify. The
   `UNVERIFIED_CITATION` pre-check fires above the kind dispatch, as documented.

## Recommendation

**Fix R12-01 before anything else, and do it by narrowing `_stem`, not by
reverting J-44.** The migraine Error-A J-44 closed is real and the fix direction
is right; what is wrong is that a one-letter strip with no part-of-speech test
is applied to the token that carries the endpoint's identity. The smallest
correct change I can defend is NOT "stem the modifiers, never the head" — that
would re-open J-44, whose whole case is the head (`migraines`/`migraine`). The
defensible move is an explicit **stem-exception list** (`news`,
`lens`, `species`, `ethics`, `damages`, `diabetes`, `series`, `means`,
`politics`, `physics`, `bias`, `status`, `crisis`, `analysis`, `campus`,
`focus`, `virus`) — a closed list of English s-final non-plurals, which is the
same lexicon argument that licenses `_SPELLED_NUMBER_WORDS`, and unlike a
suffix table it is not an open set. Error-A cost: zero on the corpus (q12's
`diabetes` would go back to literal matching, which it already satisfies).

Then R12-05 (five strings), then R12-02 (`no`/`not`/`never`/`without` out of
the endpoint stops, with a negated endpoint refused outright), then R12-03/
R12-10 (anchor the object at the FIRST content run after the trigger, not the
last — which fixes an Error-B and an Error-A with one change), then R12-04
(require the trigger to sit BETWEEN the two endpoints in the window, which is
the cheapest approximation of "relates them" available without a parser).

**The load-bearing assumption of this report:** that my hand-built store records
are equivalent to what `capture_core.py` actually writes. Every record above sets
`full_text_source: "verbatim"`, `captured_via: "inline"`, a constant

red-team fixtures use. If the real capture hook emits a field that `load_store`
reads and that changes `ground()`'s path (session scoping is the obvious
candidate, and J-38 says it does not exist yet), the gate verdicts could differ.
The per-claim verdicts and the `extract_arguments` / `_endpoint_in_window`
unit-level outputs do not depend on it.
