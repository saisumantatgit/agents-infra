## R20-01 — `"\n".join` of MCP content blocks manufactures a contiguous verbatim span that exists in NO document | CRITICAL

**Mechanism.** `_coerce_text_value` (capture_core.py:107-125) takes the standard
MCP content-block list and returns `"\n".join(parts)`. `_extract_text`
(:152-172) routes every block-list payload through it, and `make_record` stores
the single joined string as one `text` with `full_text_source="verbatim"`.
`ground_check.t1_verbatim` (:1472+) tokenizes with `re.findall(r"\w+")`, so the
`"\n"` seam **disappears**: the last tokens of block A and the first tokens of
block B become adjacent members of one n-gram index. A span that straddles the
seam satisfies T1's "contiguous verbatim span >= 8 tokens" although no retrieved
document contains it. `mcp__exa__web_fetch_exa` returns exactly this shape for a
multi-URL fetch (module docstring, lines 31-34), so the two blocks are two
DIFFERENT documents and the agent chooses both the pages and their order.

## R20-02 — A multi-URL fetch collapses N documents into ONE record whose only URL is `urls[0]` | CRITICAL

**Mechanism.** `_url_from_input` (capture_core.py:181-194) returns
`urls[0]` and discards the rest; `make_record` (:319-323) writes one record with
that single `url` and the concatenated text of ALL fetched pages. The agent
orders `urls`. Put an authoritative domain first and the page you want quoted
second: the store now asserts that the second page's sentences are text
retrieved from the first page's URL. Nothing in `RetrievedSource` can express
more than one origin, and nothing records which span came from which URL.

## R20-03 — A `Read` record can carry NO origin at all and still ground a claim at PASS 100.0 | CRITICAL

**Mechanism.** Three lines combine.
1. `_file_path_from_input` (capture_core.py:197-199) is
   `return tool_input.get("file_path") or None` — it reads ONLY `tool_input`,
   and `or None` converts `""` to `None`.
2. `make_record`'s `Read` branch (:307-314) sets `url = None` unconditionally
   and takes `file_path` from that function. The live `Read` payload carries the
   AUTHORITATIVE path at `tool_response["file"]["filePath"]` (module docstring
   lines 14-24) and capture_core **never reads it** — the only field it reads
   for the text is `file.content`.
3. `ground_check._OPTIONAL_STR_FIELDS` (:120) makes both `url` and `file_path`
   nullable, so the record validates.

So either an empty `file_path` or a harness field rename (`filePath` instead of
`file_path` — exactly the drift capture_hook's own TASK-4-VALIDATION note warns
about) yields a `verbatim` record with **zero** origin, whose text still grounds.

**Reproduction.**
```
$ cat evD.json      # tool_input uses camelCase; response carries the real path
{"session_id":"s","tool_name":"Read","tool_input":{"filePath":"/etc/hosts"},
 "tool_response":{"type":"text","file":{"filePath":"/etc/hosts","content":"Zentara sustained approximately 128000 operations per second in every tested region.","numLines":1,"startLine":1,"totalLines":1}}}
$ cat evE.json      # tool_input file_path is the empty string
{"session_id":"s","tool_name":"Read","tool_input":{"file_path":""}, ...}

$ for n in A B C D E; do ASSURE_EVIDENCE_STORE=store6.jsonl uv run python scripts/capture_hook.py < ev$n.json; echo "$n exit=$?"; done
A exit=0 stderr:
B exit=0 stderr:
C exit=0 stderr:
D exit=0 stderr:
E exit=0 stderr:
$ cat store6.jsonl   # S3 = evD, S4 = evE
{"source_id": "S3", "url": null, "file_path": null, "fetched_at": "1970-01-01T00:00:00Z", "tool": "Read", "content_sha256": "286d998e...", "text": "Zentara sustained approximately 128000 operations per second in every tested region.", "full_text_source": "verbatim", "captured_via": "inline", "query_provenance": "s", "session_id": "s"}
{"source_id": "S4", "url": null, "file_path": null, ... "tool": "Read", ...}

$ cat draftH.md
# Throughput

Zentara sustained approximately 128000 operations per second in every tested region [S3].
$ uv run python scripts/ground_check.py --draft draftH.md --store store6.jsonl --json; echo $?
gateH exit=0
PASS 100.0
[(0, 'NON_CLAIM', 'GROUNDED'), (1, 'NUMERIC', 'GROUNDED')]
```

**Why the gate cannot see it.** `_self_source_ids` (ground_check.py:4120+) has
exactly two origin tests — `os.path.samefile(source.file_path, draft_path)` and
`str(Path(source.file_path).resolve()) == draft_resolved` — and both sit behind
`if source.file_path:`. With `file_path=None` both are dead code, leaving only
the digest tests. More broadly: a record with no `url` and no `file_path` is a
verbatim certifying source whose origin the gate cannot name, print, or compare,
and it was built that way at capture. Note also the fallback: with no
`file_path`, `_derive_query_provenance` falls through to `session_id`, so the
record's "query" becomes the session id — recorded as a search that happened.

**Sibling.** `_url_from_input` has the same `or None`-style emptiness collapse
(`if isinstance(url, str) and url`), so an empty `url` from any fetch tool
produces the identical origin-free record on the WebFetch/exa/ddg branches. In
both cases the truthiness test is the only validation — `file_path` is never
checked with `isinstance`, so a non-`str` value propagates into
`append_record`'s JSON and raises in `load_store` (that one is Error-A).

## R20-04 — A FAILED retrieval is stored as verbatim content of the URL; `isError` and HTTP status are never read | HIGH

**Mechanism.** No capture path consults any error signal. `_extract_text`
dispatches purely on SHAPE: a dict with `"content"` (:160) is accepted whether
or not the sibling `isError` is `true`, and the native WebFetch envelope's
`code` / `codeText` (module docstring lines 25-29) are read by nothing. A 403, a
404 body, a captcha page or an MCP error string becomes `text` with
`full_text_source="verbatim"` and the requested URL in `url` and
`query_provenance`. The store therefore asserts a retrieval that did not happen,
and every per-source count the gate makes includes it.

**Reproduction.** Capture side (a 403 with `isError: true`):
```
$ cat evC.json
{"session_id":"s","tool_name":"mcp__exa__web_fetch_exa","tool_input":{"urls":["https://paywalled.example.com/report"]},
 "tool_response":{"content":[{"type":"text","text":"Error: crawl failed with HTTP status 403 for https://paywalled.example.com/report"}],"isError":true}}
$ ASSURE_EVIDENCE_STORE=storeC.jsonl uv run python scripts/capture_hook.py < evC.json; echo $?
exit=0
{"source_id": "S1", "url": "https://paywalled.example.com/report", "file_path": null, "fetched_at": "1970-01-01T00:00:00Z", "tool": "mcp__exa__web_fetch_exa", "content_sha256": "4dabb02e...", "text": "Error: crawl failed with HTTP status 403 for https://paywalled.example.com/report", "full_text_source": "verbatim", "captured_via": "inline", "query_provenance": "https://paywalled.example.com/report", "session_id": "s"}
```
Consumer side — two retrievals that both FAILED (403 and 404) are reported by
the gate as two searches and two retrieved sources:
```
$ uv run python scripts/ground_check.py --draft draftF.md --store storeG.jsonl --session-id sess-R20 --json; echo $?
gate exit=1
FAIL 0.0
[(0, 'NON_CLAIM', 'GROUNDED'), (1, 'ABSENCE', 'UNVERIFIED_ABSENCE')]
evidence_basis: "An absence claim is checked against what was SEARCHED, not what was cited. Complete record consulted: 2 distinct search queries and the text of 2 retrieved sources. The queries were: \"https://www.fda.gov/search?q=zentara inhaler recall notice in any regulated market\"; \"https://www.ema.europa.eu/search?q=recall notice for the zentara inhaler in any regulated market\"..."
```
**HONEST LIMIT:** this particular absence claim was REFUSED for an unrelated
reason (anchor/scope matching), so I did NOT drive this finding to a PASS. What
is demonstrated is (a) a failed fetch becomes a `verbatim` source, and (b) the
gate's own legibility surface then states as fact that 2 sources were retrieved
and 2 searches were run when neither retrieval returned any content. The
severity is HIGH rather than CRITICAL for exactly that reason.

**Why the gate cannot see it.** The error flag exists only in the live payload.
It is dropped at ingestion, so the store cannot distinguish "this URL said X"
from "this URL could not be read". `_validate_record` checks types, enum
membership and tool/source-type agreement; none of those is falsified by an
error body.

**Sibling.** `mcp__ddg-search__fetch_content` returns a plain `str`, so its
error strings take the `isinstance(tool_response, str)` fast path at
`_extract_text`:152 with no inspection at all — an even shorter route to the
same record. `WebFetch`'s `code`/`codeText` is the third.

## R20-05 — The overflow branch launders a LOCAL FILE into a URL-attributed verbatim source | HIGH (trigger shape SPECULATIVE)

**Mechanism.** `_is_overflow_payload` (capture_core.py:206-228) fires on any
dict with a non-empty `file_path` and a `preview` key and no inline
`text`/`content`. `reconstruct_text` (:249-264) then **reads that path from disk
at hook time** and stores its contents as the record's `text`. Two things follow
that no comment in the file acknowledges:
1. the stored text is the file's content at HOOK time, not the preview the model
   saw — a TOCTOU between what was shown and what is certified;
2. the branch is tool-agnostic, so on a non-`Read` tool the record's
   `file_path` stays `None` (set only in the `Read` branch, :307-314) while
   `url` is populated from `tool_input`. Content demonstrably read from a local
   file is recorded as verbatim content of a URL.

**SPECULATIVE part, stated plainly:** the module docstring says the
`{"preview","file_path"}` shape was NOT observed live (lines 43-47), so I cannot
claim a live tool emits it. The laundering below is real executed code against
the real gate; the trigger is the invented shape.

**Reproduction.**
```
$ printf 'The Zentara inhaler was cleared by the European Medicines Agency for use in every member state without conditions.\n' > fabrication.txt
$ cat evI.json
{"session_id":"sess-R20","tool_name":"mcp__exa__web_fetch_exa","tool_input":{"urls":["https://who.int/zentara-safety-review"]},
 "tool_response":{"preview":"WHO safety summary...","file_path":"<scratch>/fabrication.txt"}}
$ ASSURE_EVIDENCE_STORE=storeI.jsonl uv run python scripts/capture_hook.py < evI.json; echo $?
exit=0
{"source_id": "S1", "url": "https://who.int/zentara-safety-review", "file_path": null, "fetched_at": "1970-01-01T00:00:00Z", "tool": "mcp__exa__web_fetch_exa", "content_sha256": "b2486d4f...", "text": "The Zentara inhaler was cleared by the European Medicines Agency for use in every member state without conditions.\n", "full_text_source": "verbatim", "captured_via": "overflow_file", "query_provenance": "https://who.int/zentara-safety-review", "session_id": "sess-R20"}
$ uv run python scripts/ground_check.py --draft draftI.md --store storeI.jsonl --session-id sess-R20 --json; echo $?
gateI exit=0
PASS 100.0
[(0, 'NON_CLAIM', 'GROUNDED'), (1, 'FACTUAL', 'GROUNDED')]
```

**Why the gate cannot see it.** `captured_via="overflow_file"` is the only trace,
and it is not in any validation list: `_validate_record` requires it to be a
`str` and nothing more, and no verdict branch reads it. The gate has no rule
that a record read from a local file must carry a `file_path`, so a record whose
two provenance fields actively contradict its own capture path is valid audit
evidence.

**Sibling.** The same contradiction is available on the `Read` branch in reverse:
a `Read` whose overflow payload points at a different file records
`file_path` from `tool_input` while the text comes from the overflow path — one
field names a file and the text came from another. Both reduce to the same
missing invariant: `captured_via` is never cross-checked against the origin
fields.

## R20-06 — An empty or whitespace response is admitted as a `verbatim` source, while an empty block LIST is refused | MEDIUM

**Mechanism.** `_coerce_text_value` refuses an empty block list explicitly
(:121-124, "Empty content-block list — no text blocks to store"), and
`_extract_text` returns `tool_response` unchanged for a plain `str` (:152-153)
and `_coerce_text_value("")` -> `""` for `{"text": ""}`. So the SAME emptiness is
fail-closed through one door and fail-open through another. The admitted record
is a citable `verbatim` source with `text=""` (its `content_sha256` is the
well-known SHA-256 of the empty string) and a `query_provenance` the gate counts
as a distinct search.

**Reproduction.** (same run as R20-03; events A and B)
```
$ cat evA.json
{"session_id":"s","tool_name":"mcp__ddg-search__fetch_content","tool_input":{"url":"https://example.com/a"},"tool_response":""}
$ cat evB.json
{"session_id":"s","tool_name":"mcp__exa__web_fetch_exa","tool_input":{"urls":["https://example.com/b"]},"tool_response":{"text":"   "}}
A exit=0 stderr:
B exit=0 stderr:
$ head -2 store6.jsonl
{"source_id": "S1", "url": "https://example.com/a", ..., "content_sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855", "text": "", "full_text_source": "verbatim", "captured_via": "inline", "query_provenance": "https://example.com/a", "session_id": "s"}
{"source_id": "S2", "url": "https://example.com/b", ..., "text": "   ", "full_text_source": "verbatim", ...}
```
No reproduction drove an empty source to a PASS on its own, hence MEDIUM. What
it does is inflate every population the gate counts over — distinct queries for
the absence minimum, cited sources for the relational rule, `source_texts` for
the contradiction check (where empty text can never contradict anything) —
with sources that carry no evidence. Per CLAUDE.md's round-4 rule, "the
retrieval returned nothing" is an I-don't-know, and here it points toward PASS.

**Why the gate cannot see it.** `_REQUIRED_STR_FIELDS` requires `text` to be a
`str`; `""` is a `str`. There is no non-empty constraint anywhere in
`_validate_record`, and there cannot usefully be one added later without
rejecting stores already written.

**Sibling.** `make_record` has no post-condition on `text` at all, so the same
hole exists on every branch — including the `Read` branch reading a genuinely
empty file, which is the benign case the rule has to separate from the
"retrieval returned nothing" case. The capture layer currently cannot tell them
apart because it records no outcome, only a shape (see R20-04).

## SPECULATIVE / NOT REPRODUCED

- **`is_retrieval_tool` is exact-string membership** (`capture_core.py:81-88`),
  mirrored in `ground_check._VERBATIM_TOOLS`. The bare name `web_fetch_exa` is
  trusted as verbatim, so ANY locally-configured MCP server or custom tool that
  happens to be named `web_fetch_exa` inherits verbatim trust in both halves.
  Conversely the same server mounted under a different prefix
  (`mcp__exa2__web_fetch_exa`) is not captured at all — that direction is
  Error-A. Not reproduced: it needs a tool-registration change, not a payload.
- **Store identity / rotation beyond J-38.** `_resolve_store_path`
  (capture_hook.py:68-77) defaults to `Path.cwd()/".assure"/...`, so the store
  a hook writes depends on the hook process's CWD, and `next_source_id` restarts
  at `S1` against any fresh or emptied file. A draft citing `[S1]` therefore
  names different evidence in different store files. Mentioned because it is
  capture-side and distinct from "never rotated"; not reproduced as an Error-B.
- **`next_source_id` skips lines that fail `json.loads` (`continue`, :370-372)
  while `load_store` RAISES on them.** The two disagree about what the store
  contains. I could not construct an Error-B from it (the loader's refusal
  dominates); recorded so the asymmetry is on file.

## THE LOAD-BEARING ASSUMPTION OF THIS REPORT

Every finding assumes the hook event fields (`tool_name`, `tool_input`,
`tool_response`) can hold the shapes I fed them. For R20-01, R20-02 and R20-04
the shapes are the ones the module docstring itself documents as LIVE-VALIDATED
(multi-block exa lists, plural `urls`, dict `content`), so those stand without
further evidence. For R20-03 the shape is a FIELD-NAME DRIFT or an empty string
in `tool_input`, which is plausible but unobserved; for R20-05 the trigger shape
is documented as never observed. If the live harness can never produce those two
shapes, R20-03 and R20-05 reduce from live attacks to latent defects — the code
paths are real either way. Checking this needs one real session's raw PostToolUse
payloads, which is the usage instrument this round did not have.
