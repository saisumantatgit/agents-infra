## Findings

### HIGH-1: exa documents are still joined in the overflow, plain-str and `{"text": str}` shapes, but the docstrings promise they are not (R15-01 class)
- **Where:** `scripts/capture_core.py`, in `_documents` and `_block_list` (around lines 440-500), and `make_records` (around line 520).
- **What is wrong:** `_documents` splits on exa section headers only when `_block_list` returns a block LIST. When the response is an overflow payload (`{"preview", "file_path"}`), a bare `str`, or a dict whose `"text"` is a str, `_block_list` returns None. In those cases `make_records` falls back to `make_record` and stores the whole multi-page fetch as ONE record.
- **Docstrings this contradicts:** "a multi-document response (separate blocks, or exa sections inside one block) yields one record per document, so no span crosses between them." The comment at `make_record` ("R20-01: a single record for a multi-document response would glue...") makes the same promise.
- **Concrete input (reproduced):** exa with `urls=[a, b]` and the body `"# A\nURL: a\nThe bank raised\n# B\nURL: b\nrates to five percent."`.
  - Overflow dict, str and `{"text": str}` each give **1 record**.
  - The block-list shape gives 2 records.
  - In the 1-record shapes, the verbatim span "The bank raised rates to five percent." crosses from page A into page B, which is the exact R20-01 attack.
- **Where it bites in practice:** the overflow shape is the most likely one for a large multi-URL fetch. That is the case R20-01 exists for.
- **Is it a regression?** No. Main joined everything, so this is a residual hole, not a new one.
- **Fix:** for `tool_name in _EXA_TOOLS`, apply `_EXA_SECTION_LOOSE_RE.split` to the RECONSTRUCTED text (the `reconstruct_text` output) whatever the response shape, not only inside `_block_list`. Add a test for each of the three shapes, run red on the current code first.

### MEDIUM-1: the absence display still counts failed fetches as "retrieved sources"
- **Where:** `scripts/ground_check.py:4000`, `n_src = sum(1 for s in store.values() if s.text)`.
- **What is wrong:** a failed fetch keeps its error body as text, so it still counts toward "the text of N retrieved sources". The R20 comment says the report "said 'the text of 2 retrieved sources' when both fetches had failed", and implies this is fixed. The fix only adds a note that names the uncounted queries; the headline "2 retrieved sources" is unchanged.
- **Fix:** count with `_carries_retrieved_content`, or label the number as "stored records".
- **Severity reason:** display only, not decision.

### MEDIUM-2: the display does not explain the new BASIS refusal
- **Where:** `ground_check.py` around line 3598 (R21-03).
- **What is wrong:** the verdict now returns UNVERIFIED_ABSENCE when no verbatim source returned content. `evidence_basis` has no branch that says so.
- **Concrete reading:** two WebFetch summaries (`ok`) plus one exa fetch with status `failed`, with all queries countable. The display shows no `no_content_note` for the summary queries, yet the verdict refuses.
- **Effect:** the decision is right, but the reason shown for it is missing. This is a display/decision agreement gap: the two read different predicates.
- **Fix:** add a sentence when `not any(verbatim and _carries_retrieved_content and not self)` holds, reading the same expression the verdict reads.
